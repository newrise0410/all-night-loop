# 지시서(SPEC) 작성 가이드 — 5요소

자율 루프의 품질은 전부 SPEC에서 결정된다. 루프는 SPEC보다 똑똑해지지 않는다.
아래 5요소가 빠지면 밤새 돌려도 아침에 쓸 수 있는 결과가 안 나온다.

---

## 1. 합격 기준 (Acceptance Criteria)

**무엇**: "언제 이 작업이 끝난 것인가"를 기계가 판정할 수 있게 적는다.

퀄리티를 유지하는 최종 관문은 이 한 문장이다:

> **"다른 사람이 봐도 괜찮은가?"**

이걸 자기 자신에게 물어보게 만드는 게 목적이다. 하지만 이것만 있으면 주관적이므로,
**실행 가능한 명령**과 짝지어라.

```markdown
## 합격 기준
- [ ] `npm test` 전부 통과 (실패 0)
- [ ] `npm run lint` 경고 0
- [ ] 새 함수에 테스트가 최소 1개 있다
- [ ] diff가 200줄 이하다 (넘으면 작업을 쪼갠 것)
- [ ] **다른 사람이 리뷰해도 통과시킬 수준인가?** — 임시 변수명, 주석 처리된 코드,
      TODO 남김, 디버그 print 가 없어야 한다
```

나쁜 예: "잘 동작할 것", "코드가 깔끔할 것" → 판정 불가 → 루프가 제멋대로 통과 선언한다.

---

## 2. 참조 파일 지정 (Reference Files)

**무엇**: 읽어야 할 파일 목록과 **범위**.

**왜**: 범위를 안 주면 루프는 저장소 전체를 탐색하며 컨텍스트를 태우고,
엉뚱한 파일을 "관련 있어 보인다"며 고친다.

```markdown
## 참조 파일
반드시 읽을 것:
- `src/api/router.ts` — 라우팅 등록 위치. 새 엔드포인트는 여기에만 추가
- `src/db/schema.sql` — 스키마. 읽기만, 수정 금지
- `docs/api-convention.md` — 응답 포맷 규약

읽지 말 것 (시간 낭비):
- `legacy/**` — 폐기 예정
- `node_modules/**`, `dist/**`
```

## 3. 규칙과 근거 (Rules + Why)

**무엇**: 지켜야 할 규칙. **규칙 뒤에 반드시 "왜"를 붙인다.**

**왜 "왜"가 필요한가**: 이유 없는 규칙은 상황이 조금만 달라지면 "이 경우는 예외겠지"라며
깨진다. 이유가 있으면 처음 보는 상황에서도 규칙의 의도대로 판단한다.
규칙 준수율이 눈에 띄게 올라간다.

```markdown
## 규칙
- 새 의존성을 추가하지 않는다
  → **왜**: 새벽에 추가된 패키지는 아무도 검토하지 않는다. 라이선스·취약점 리스크.
- 파일당 300줄을 넘기지 않는다
  → **왜**: 넘어가면 다음 세션이 파일 전체를 읽느라 컨텍스트를 다 쓴다.
- DB 마이그레이션은 만들지 않는다
  → **왜**: 되돌리기 어렵고, 사람 승인 없이 스키마가 바뀌면 아침에 복구 비용이 크다.
- 에러는 삼키지 말고 위로 던진다
  → **왜**: 조용히 실패하면 루프가 "통과"로 오판하고 그 위에 계속 쌓는다.
```

## 4. 작업 순서 (Order of Operations)

**무엇**: 고정된 단계 순서. **읽기 → 만들기 → 확인 → 커밋 → 기록**

**왜**: 순서가 없으면 루프는 "만들기"부터 시작한다. 읽지 않고 만들면 중복 구현이 나오고,
확인 없이 커밋하면 깨진 상태가 저장된다.

```markdown
## 작업 순서
1. 읽기   — SPEC / HANDOFF / BACKLOG / git log / 참조 파일
2. 만들기 — 작업 1개만 구현
3. 확인   — 검증 명령 실행 + 합격 기준 대조
4. 커밋   — 통과 즉시
5. 기록   — HANDOFF / JOURNAL / BACKLOG 갱신 후 커밋
```

---

## 5. 커밋 순서 (Commit Timing)

**무엇**: **검사 통과 직후 즉시 커밋.** 기록·정리·다음 작업보다 먼저.

**왜**: 자율 루프는 도중에 멈춘다 — 컨텍스트 한계, 사용자 중단, 도구 실패.
통과한 상태를 커밋하지 않고 다른 일을 하다 멈추면 그 사이클의 노동이 전부 사라진다.
커밋은 "여기까지는 확실하다"는 세이브 포인트다.

```markdown
## 커밋 규칙
- 검증 통과 → **즉시** `git add -A && git commit`. 사이에 아무것도 끼우지 않는다.
- 커밋 단위 = 작업 1개. 뭉치지 않는다.
- 메시지에 검증 결과를 남긴다 (`검증: npm test 42 passed`)
- 금지: push / --force / reset --hard / 히스토리 재작성
  → **왜**: 되돌리기 어려운 조작은 사람이 깨어 있을 때만.
```

---

## 체크리스트

SPEC을 다 썼으면 이걸 확인하라:

- [ ] 합격 기준에 **실행 가능한 명령**이 하나 이상 있다
- [ ] "다른 사람이 봐도 괜찮은가" 류의 품질 관문이 있다
- [ ] 참조 파일에 **읽을 것**과 **읽지 말 것**이 둘 다 있다
- [ ] 모든 규칙에 **왜**가 붙어 있다
- [ ] 작업 순서가 읽기→만들기→확인→커밋→기록 으로 고정돼 있다
- [ ] 커밋 타이밍이 "검증 통과 즉시"로 못 박혀 있다
- [ ] 이 SPEC만 읽고 처음 보는 사람이 첫 작업을 시작할 수 있다
