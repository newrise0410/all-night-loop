# all-night-spec

# All-Night Spec — 지시서 작성

주제를 받아 **`loop/SPEC.md` 와 `loop/BACKLOG.md` 를 쓴다.** 그게 전부다.

## 절대 하지 않는 것

- **구현을 시작하지 않는다.** 코드 파일을 만들거나 고치지 않는다.
  → **왜**: 지시서를 쓰라고 불렀는데 코드를 짜기 시작하면, 합격 기준 없이 작업이 시작된다.
    그건 자율 루프가 밤새 쓰레기를 만드는 가장 흔한 경로다.
- `loop/HANDOFF.md`·`loop/JOURNAL.md` 를 채우지 않는다. 루프가 쓸 파일이다.

## 절차

### 1. 조사 — 추측하지 말고 확인한다

주제만으로 SPEC 을 쓰면 반드시 틀린다. **저장소를 먼저 읽는다.**

- 빌드/테스트 설정: `package.json`(scripts), `Makefile`, `pyproject.toml`, `Cargo.toml`,
  `go.mod`, `build.gradle`, `*.csproj` 등 있는 것
- CI 설정: `.github/workflows/*`, `.gitlab-ci.yml` — **실제로 무엇을 검사하는지**가 여기 있다
- 기존 규약: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `README.md`, `.editorconfig`, 린터 설정
- 코드 구조: 최상위 디렉터리와 주제에 관련된 파일 몇 개
- `git log --oneline -20` — 커밋 메시지 관례(prefix, 언어)를 여기서 읽는다

빈 저장소라면 그 사실을 SPEC 에 적고, 검증 명령은 "무엇을 만들면 그때 무엇이 검사 명령이 되는지"로 쓴다.

### 2. 검증 명령 확정 — 지어내지 않는다

합격 기준의 핵심은 **실제로 돌아가는 명령**이다.

- `package.json` 의 `scripts` 에 있는 것만 쓴다. 없는 `npm run lint` 를 적지 않는다.
  → **왜**: 존재하지 않는 명령은 루프가 "통과"로 오판하거나 매 사이클 실패한다. 둘 다 밤을 날린다.
- 확신이 서면 한 번 실행해서 실제로 도는지 확인한다.
- 검사 도구가 아예 없으면, **검사 도구를 세우는 것 자체를 BACKLOG 의 첫 작업**으로 넣는다.

### 3. SPEC 작성 — 5요소

`loop/SPEC.md` 를 다음 5요소로 채운다. 템플릿이 이미 있으면 자리표시자를 실제 내용으로 바꾼다.

1. **합격 기준** — 실행 가능한 검증 명령 + `"다른 사람이 리뷰해도 통과시킬까?"` 품질 관문
2. **참조 파일** — 읽을 것 / 수정 금지 / 읽지 말 것. **범위까지** 적는다
3. **규칙과 근거** — 모든 규칙 뒤에 `→ **왜**:` 를 붙인다
   → **왜**: 이유 없는 규칙은 처음 보는 상황에서 "이 경우는 예외겠지"로 깨진다
4. **작업 순서** — 읽기 → 만들기 → 확인 → 커밋 → 기록
5. **커밋 규칙** — 검증 통과 즉시 커밋, 커밋 1개 = 작업 1개, 브랜치·push 정책

자리표시자(`<...>`)를 **하나도 남기지 않는다.** 모르는 값은 추측 대신 저장소에서 확인하고,
정말 알 수 없으면 그 항목을 "사람에게 확인 필요"로 명시한다.

### 4. BACKLOG 작성 — 한 사이클 크기로 쪼갠다

`loop/BACKLOG.md` 에 작업을 `T001` 부터 번호를 붙여 적는다.

- **한 항목 = 한 사이클 = 한 커밋.** "diff 200줄 이하로 끝나나?" 를 기준으로 쪼갠다.
  → **왜**: 항목이 크면 루프가 도중에 끊겼을 때 남는 게 없다.
- 의존 순서대로 나열한다. 앞 항목이 끝나야 뒤 항목이 가능하도록.
- 첫 항목은 **가장 작고 확실한 것**으로 둔다.
  → **왜**: 첫 사이클이 성공해야 루프가 궤도에 오른다. 첫 항목이 크면 3회 실패로 멈춘다.
- 각 항목에 그 항목만의 완료 조건이 있으면 한 줄 덧붙인다.
- 주제 범위 밖이지만 해두면 좋을 것은 `[?]` 로 적는다. 루프는 `[?]` 를 실행하지 않는다.

### 5. 보고

무엇을 근거로 무엇을 정했는지 짧게 보고한다. 특히:

- 검증 명령을 무엇으로 정했고 **어디서 찾았는지**
- 추측한 부분 / 사람 확인이 필요한 부분
- BACKLOG 항목 수와 첫 작업

`loop/SPEC.md` 를 사람이 훑어보고 고칠 수 있게, 확신이 낮은 항목은 명시적으로 짚어준다.
→ **왜**: SPEC 은 사람이 승인하는 마지막 지점이다. 여기서 잘못된 전제가 통과하면 밤새 증폭된다.

## 인터뷰 답변이 함께 주어진 경우

프롬프트에 `## 인터뷰 답변` 블록이 있으면 **그것이 저장소 조사보다 우선한다.**
사람이 직접 답한 내용이기 때문이다. 다만:

- 빈 답변은 저장소 조사로 채운다
- 답변과 저장소가 모순되면(예: "npm test" 라 했는데 scripts 에 없다) **답변을 따르되 SPEC 에 그 불일치를 적는다**
  → **왜**: 사람이 곧 만들 예정일 수 있다. 조용히 바꾸면 사람이 의도한 바가 사라진다.

# 부록 — 지시서(SPEC) 작성 5요소 상세

> 위 절차 3단계에서 쓸 기준이다.

자율 루프의 품질은 전부 SPEC에서 결정된다. 루프는 SPEC보다 똑똑해지지 않는다.
아래 5요소가 빠지면 밤새 돌려도 아침에 쓸 수 있는 결과가 안 나온다.

---

## 1. 합격 기준 (Acceptance Criteria)

**무엇**: "언제 이 작업이 끝난 것인가"를 기계가 판정할 수 있게 적는다.

퀄리티를 유지하는 최종 관문은 이 한 문장이다:

> **"다른 사람이 봐도 괜찮은가?"**

이걸 자기 자신에게 물어보게 만드는 게 목적이다. 하지만 이것만 있으면 주관적이므로,
**실행 가능한 명령**과 짝지어라.

```markdown
## 합격 기준
- [ ] `npm test` 전부 통과 (실패 0)
- [ ] `npm run lint` 경고 0
- [ ] 새 함수에 테스트가 최소 1개 있다
- [ ] diff가 200줄 이하다 (넘으면 작업을 쪼갠 것)
- [ ] **다른 사람이 리뷰해도 통과시킬 수준인가?** — 임시 변수명, 주석 처리된 코드,
      TODO 남김, 디버그 print 가 없어야 한다
```

나쁜 예: "잘 동작할 것", "코드가 깔끔할 것" → 판정 불가 → 루프가 제멋대로 통과 선언한다.

---

## 2. 참조 파일 지정 (Reference Files)

**무엇**: 읽어야 할 파일 목록과 **범위**.

**왜**: 범위를 안 주면 루프는 저장소 전체를 탐색하며 컨텍스트를 태우고,
엉뚱한 파일을 "관련 있어 보인다"며 고친다.

```markdown
## 참조 파일
반드시 읽을 것:
- `src/api/router.ts` — 라우팅 등록 위치. 새 엔드포인트는 여기에만 추가
- `src/db/schema.sql` — 스키마. 읽기만, 수정 금지
- `docs/api-convention.md` — 응답 포맷 규약

읽지 말 것 (시간 낭비):
- `legacy/**` — 폐기 예정
- `node_modules/**`, `dist/**`
```

---

## 3. 규칙과 근거 (Rules + Why)

**무엇**: 지켜야 할 규칙. **규칙 뒤에 반드시 "왜"를 붙인다.**

**왜 "왜"가 필요한가**: 이유 없는 규칙은 상황이 조금만 달라지면 "이 경우는 예외겠지"라며
깨진다. 이유가 있으면 처음 보는 상황에서도 규칙의 의도대로 판단한다.
규칙 준수율이 눈에 띄게 올라간다.

```markdown
## 규칙
- 새 의존성을 추가하지 않는다
  → **왜**: 새벽에 추가된 패키지는 아무도 검토하지 않는다. 라이선스·취약점 리스크.
- 파일당 300줄을 넘기지 않는다
  → **왜**: 넘어가면 다음 세션이 파일 전체를 읽느라 컨텍스트를 다 쓴다.
- DB 마이그레이션은 만들지 않는다
  → **왜**: 되돌리기 어렵고, 사람 승인 없이 스키마가 바뀌면 아침에 복구 비용이 크다.
- 에러는 삼키지 말고 위로 던진다
  → **왜**: 조용히 실패하면 루프가 "통과"로 오판하고 그 위에 계속 쌓는다.
```

---

## 4. 작업 순서 (Order of Operations)

**무엇**: 고정된 단계 순서. **읽기 → 만들기 → 확인 → 커밋 → 기록**

**왜**: 순서가 없으면 루프는 "만들기"부터 시작한다. 읽지 않고 만들면 중복 구현이 나오고,
확인 없이 커밋하면 깨진 상태가 저장된다.

```markdown
## 작업 순서
1. 읽기   — SPEC / HANDOFF / BACKLOG / git log / 참조 파일
2. 만들기 — 작업 1개만 구현
3. 확인   — 검증 명령 실행 + 합격 기준 대조
4. 커밋   — 통과 즉시
5. 기록   — HANDOFF / JOURNAL / BACKLOG 갱신 후 커밋
```

---

## 5. 커밋 순서 (Commit Timing)

**무엇**: **검사 통과 직후 즉시 커밋.** 기록·정리·다음 작업보다 먼저.

**왜**: 자율 루프는 도중에 멈춘다 — 컨텍스트 한계, 사용자 중단, 도구 실패.
통과한 상태를 커밋하지 않고 다른 일을 하다 멈추면 그 사이클의 노동이 전부 사라진다.
커밋은 "여기까지는 확실하다"는 세이브 포인트다.

```markdown
## 커밋 규칙
- 검증 통과 → **즉시** `git add -A && git commit`. 사이에 아무것도 끼우지 않는다.
- 커밋 단위 = 작업 1개. 뭉치지 않는다.
- 메시지에 검증 결과를 남긴다 (`검증: npm test 42 passed`)
- 금지: push / --force / reset --hard / 히스토리 재작성
  → **왜**: 되돌리기 어려운 조작은 사람이 깨어 있을 때만.
```

---

## 체크리스트

SPEC을 다 썼으면 이걸 확인하라:

- [ ] 합격 기준에 **실행 가능한 명령**이 하나 이상 있다
- [ ] "다른 사람이 봐도 괜찮은가" 류의 품질 관문이 있다
- [ ] 참조 파일에 **읽을 것**과 **읽지 말 것**이 둘 다 있다
- [ ] 모든 규칙에 **왜**가 붙어 있다
- [ ] 작업 순서가 읽기→만들기→확인→커밋→기록 으로 고정돼 있다
- [ ] 커밋 타이밍이 "검증 통과 즉시"로 못 박혀 있다
- [ ] 이 SPEC만 읽고 처음 보는 사람이 첫 작업을 시작할 수 있다
