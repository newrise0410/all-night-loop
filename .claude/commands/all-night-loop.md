# all-night-loop

# All-Night Loop — 한 사이클

사람이 지켜보지 않는 동안 스스로 개발을 이어가기 위한 **1회분 사이클**이다.
이 스킬은 **한 번 호출 = 작업 하나 = 커밋 하나 = 기록 하나**로 끝난다. 반복은 `/loop`이 담당한다.

## 왜 한 번에 하나만 하는가 (이 스킬의 핵심 전제)

- **왜 하나만**: 세션은 언제든 끊긴다(컨텍스트 초과, 사용자 중단, 크래시). 작업 단위가 크면 끊겼을 때 남는 게 없다. 하나씩 끝내면 끊겨도 직전까지가 온전히 남는다.
- **왜 즉시 커밋**: 검증을 통과했는데 커밋 전에 죽으면 그 노동은 0이 된다. 커밋은 "여기까지는 확실하다"는 세이브 포인트다.
- **왜 인수인계 기록**: 다음 사이클의 나는 지금의 기억이 전혀 없는 남이다. 코드만 봐서는 "왜 이렇게 했는지 / 다음에 뭘 해야 하는지"를 복원할 수 없다.
- **왜 스코프를 안 넓히는가**: 감시자가 없을 때 스코프가 번지면 아침에 되돌릴 수 없는 변경 더미가 쌓인다. SPEC 밖의 아이디어는 *실행*이 아니라 *제안*으로만 남긴다.

## 파일 규약

모든 상태는 저장소 안 `loop/` 에 텍스트로 산다. **기억이 아니라 파일이 단일 진실 공급원이다.**

| 파일 | 역할 | 누가 쓰나 |
|---|---|---|
| `loop/SPEC.md` | 지시서. 무엇을/왜/어디까지. **읽기 전용** | 사람 |
| `loop/BACKLOG.md` | 작업 목록. 상태 표시(`[ ] / [~] / [x] / [!]`) | 루프 |
| `loop/HANDOFF.md` | 다음 세션에게 주는 인수인계. **매번 덮어씀** | 루프 |
| `loop/JOURNAL.md` | 사이클별 append-only 로그 | 루프 |

상태 기호: `[ ]` 대기 · `[~]` 진행중(중단됨) · `[x]` 완료 · `[!]` 막힘

## 실행 순서

> 순서를 지켜라. 특히 **4(검증) → 5(커밋)** 사이에 다른 일을 끼워 넣지 마라. 통과한 상태를 즉시 고정하는 것이 이 루프의 유일한 안전장치다.

### 0. 부트스트랩 체크
`loop/SPEC.md`가 없으면 → **작업을 시작하지 말고** `reference/spec-writing.md`를 읽고 `templates/`로 `loop/` 를 만든 뒤 사용자에게 SPEC 초안 확인을 요청하고 멈춘다.
(왜: 합격 기준 없는 자율 실행은 밤새 쓰레기를 생산하는 가장 빠른 방법이다.)

### 1. 읽기 — 상태 복원
아래를 **전부** 읽는다. 하나라도 건너뛰면 이미 한 일을 다시 하거나 규칙을 어긴다.
1. `loop/SPEC.md` — 합격 기준·규칙·참조 파일 목록
2. `loop/HANDOFF.md` — 직전 세션이 남긴 다음 할 일과 주의사항
3. `loop/BACKLOG.md` — 남은 작업
4. `git log --oneline -10` 과 `git status` — 기록과 실제가 어긋나는지 확인
5. SPEC의 "참조 파일"에 적힌 파일들 (거기 적힌 범위만)

`git status`가 더러우면(uncommitted 변경) → 직전 세션이 커밋 전에 죽은 것이다. HANDOFF의 `[~]` 항목을 이어서 마무리하는 것이 이번 작업이다.

### 2. 고르기 — 작업 하나
우선순위: `[~]` 진행중 → HANDOFF의 "다음 작업" → `[!]` 아닌 `[ ]` 중 최상단.
- 고른 항목을 `[~]`로 바꾸고 BACKLOG에 착수 시각을 적는다.
- **하나만 고른다.** "이건 5초면 되니까 같이" 는 금지. 그 5초짜리가 다음 커밋을 오염시킨다.
- 한 사이클로 끝낼 수 없어 보이면 → 쪼개서 BACKLOG에 하위 항목으로 적고, 그 중 첫 번째만 한다.

### 3. 만들기 — 구현
- SPEC의 규칙을 지킨다. 규칙과 내 취향이 충돌하면 규칙이 이긴다.
- 기존 코드의 스타일·네이밍·구조를 따른다. (왜: 밤새 만든 코드가 아침에 이질적으로 보이면 결국 다시 짜게 된다.)
- SPEC에 없는 리팩터링·의존성 추가·설정 변경은 하지 않는다. 필요하면 BACKLOG에 `[ ] (제안)` 으로 적는다.

### 4. 확인 — 합격 기준 대조
SPEC의 **검증 명령을 실제로 실행**한다. 실행하지 않은 것을 "통과"라고 적지 않는다.
그 다음 SPEC의 합격 기준을 항목별로 자문한다. 특히:
> **"이 diff를 내가 아닌 다른 사람이 리뷰해도 통과시킬까?"** — 아니면 아직 4단계다.

- **통과** → 5로 간다.
- **실패** → 고쳐서 다시 4를 돈다. 단 **같은 작업 3회 실패 시 중단**: 커밋하지 말고, 작업을 `[!]`로 표시, HANDOFF에 실패한 증상·시도한 것·마지막 에러 원문을 적고 7로 간다. (왜: 실패를 무한 반복하는 루프는 토큰만 태우고 상태를 더 망가뜨린다.)

### 5. 커밋 — 즉시
검증 통과 직후, 다른 어떤 작업보다 먼저 커밋한다.

```
git add -A && git commit -m "<type>: <한 줄 요약>

- 무엇을 왜 바꿨는지 2~4줄
- 검증: <실행한 명령과 결과>

Task: <BACKLOG 항목 ID>
"
```
- 브랜치가 보호 대상(main 등)이고 SPEC이 브랜치 사용을 지시했다면 먼저 브랜치를 만든다.
- **금지**: `push`(SPEC이 명시 허용한 경우 제외), `--force`, `reset --hard`, 히스토리 재작성, 비밀키 커밋.
  (왜: 되돌리기 어려운 조작은 사람이 깨어 있을 때만 해야 한다.)

### 6. 기록 — 인수인계
세 파일을 갱신하고 **한 번 더 커밋**한다(`chore: loop log`).

1. `BACKLOG.md` — 이번 항목 `[x]`(또는 `[!]`), 새로 알게 된 할 일 추가
2. `HANDOFF.md` — 템플릿 형식 그대로 **덮어쓰기**. 다음 세션이 이것만 읽고도 즉시 출발할 수 있어야 한다.
3. `JOURNAL.md` — 맨 아래에 이번 사이클 블록 **추가만**(기존 줄 수정 금지)

HANDOFF에 반드시 들어가야 하는 것: 방금 한 일 / 커밋 해시 / **다음에 할 일 한 줄** / 함정·주의사항 / 건드리지 말 것.
"다음에 할 일"을 비워두지 마라. 비면 다음 사이클은 처음부터 다시 판단해야 하고, 그때 판단이 흔들린다.

### 7. 종료
한 줄로 보고하고 **멈춘다**. 이어서 다음 작업을 시작하지 않는다.
```
[loop] <작업ID> <완료|막힘> · <커밋해시> · 다음: <다음 작업 한 줄>
```

## 무한 반복 걸기

이 스킬은 **한 사이클**만 정의한다. 반복은 바깥 하네스가 돌린다.

```bash
anloop loop --agent claude     # 또는 codex / gemini / cursor / opencode / aider
anloop loop --cmd "mycli -p {prompt}"   # 임의의 CLI
```

Claude Code 안에서는 `/loop /all-night-loop` 도 같은 역할을 한다.

## 루프 종료 신호

다음 경우 **마지막 줄에 아래 문장을 그대로 출력**하고 멈춘다. 바깥 하네스가 이 문장을 보고 루프를 끝낸다.

- BACKLOG에 `[ ]`/`[~]` 항목이 하나도 없다 → `[loop] ALL DONE`
- `[!]`로 막힌 항목뿐이다 → `[loop] BLOCKED`
- SPEC이 모호해 판단이 불가능하다 → `[loop] NEEDS SPEC`

같은 값을 `loop/HANDOFF.md`의 `상태` 필드에도 적는다. (왜: stdout은 유실될 수 있지만 파일은 남는다.)
멈출 때도 6단계(기록)는 반드시 먼저 한다.

## 자주 깨지는 지점

| 증상 | 원인 | 처방 |
|---|---|---|
| 아침에 커밋은 많은데 쓸 게 없다 | 합격 기준이 추상적 | SPEC의 검증 명령을 실행 가능한 명령어로 |
| 같은 작업을 계속 다시 함 | HANDOFF "다음 작업"이 빔 | 6단계를 건너뛰지 말 것 |
| 스코프가 밤새 번짐 | 제안을 실행해버림 | 3단계 규칙: SPEC 밖은 BACKLOG에만 |
| 커밋이 뭉텅이 | 한 사이클에 여러 작업 | 2단계 "하나만" |

# 부록 — 지시서(SPEC) 작성 가이드

> `loop/SPEC.md` 가 비어 있거나 없을 때만 필요하다. 이미 채워져 있으면 읽지 않아도 된다.

자율 루프의 품질은 전부 SPEC에서 결정된다. 루프는 SPEC보다 똑똑해지지 않는다.
아래 5요소가 빠지면 밤새 돌려도 아침에 쓸 수 있는 결과가 안 나온다.

---

## 1. 합격 기준 (Acceptance Criteria)

**무엇**: "언제 이 작업이 끝난 것인가"를 기계가 판정할 수 있게 적는다.

퀄리티를 유지하는 최종 관문은 이 한 문장이다:

> **"다른 사람이 봐도 괜찮은가?"**

이걸 자기 자신에게 물어보게 만드는 게 목적이다. 하지만 이것만 있으면 주관적이므로,
**실행 가능한 명령**과 짝지어라.

```markdown
## 합격 기준
- [ ] `npm test` 전부 통과 (실패 0)
- [ ] `npm run lint` 경고 0
- [ ] 새 함수에 테스트가 최소 1개 있다
- [ ] diff가 200줄 이하다 (넘으면 작업을 쪼갠 것)
- [ ] **다른 사람이 리뷰해도 통과시킬 수준인가?** — 임시 변수명, 주석 처리된 코드,
      TODO 남김, 디버그 print 가 없어야 한다
```

나쁜 예: "잘 동작할 것", "코드가 깔끔할 것" → 판정 불가 → 루프가 제멋대로 통과 선언한다.

---

## 2. 참조 파일 지정 (Reference Files)

**무엇**: 읽어야 할 파일 목록과 **범위**.

**왜**: 범위를 안 주면 루프는 저장소 전체를 탐색하며 컨텍스트를 태우고,
엉뚱한 파일을 "관련 있어 보인다"며 고친다.

```markdown
## 참조 파일
반드시 읽을 것:
- `src/api/router.ts` — 라우팅 등록 위치. 새 엔드포인트는 여기에만 추가
- `src/db/schema.sql` — 스키마. 읽기만, 수정 금지
- `docs/api-convention.md` — 응답 포맷 규약

읽지 말 것 (시간 낭비):
- `legacy/**` — 폐기 예정
- `node_modules/**`, `dist/**`
```

---

## 3. 규칙과 근거 (Rules + Why)

**무엇**: 지켜야 할 규칙. **규칙 뒤에 반드시 "왜"를 붙인다.**

**왜 "왜"가 필요한가**: 이유 없는 규칙은 상황이 조금만 달라지면 "이 경우는 예외겠지"라며
깨진다. 이유가 있으면 처음 보는 상황에서도 규칙의 의도대로 판단한다.
규칙 준수율이 눈에 띄게 올라간다.

```markdown
## 규칙
- 새 의존성을 추가하지 않는다
  → **왜**: 새벽에 추가된 패키지는 아무도 검토하지 않는다. 라이선스·취약점 리스크.
- 파일당 300줄을 넘기지 않는다
  → **왜**: 넘어가면 다음 세션이 파일 전체를 읽느라 컨텍스트를 다 쓴다.
- DB 마이그레이션은 만들지 않는다
  → **왜**: 되돌리기 어렵고, 사람 승인 없이 스키마가 바뀌면 아침에 복구 비용이 크다.
- 에러는 삼키지 말고 위로 던진다
  → **왜**: 조용히 실패하면 루프가 "통과"로 오판하고 그 위에 계속 쌓는다.
```

---

## 4. 작업 순서 (Order of Operations)

**무엇**: 고정된 단계 순서. **읽기 → 만들기 → 확인 → 커밋 → 기록**

**왜**: 순서가 없으면 루프는 "만들기"부터 시작한다. 읽지 않고 만들면 중복 구현이 나오고,
확인 없이 커밋하면 깨진 상태가 저장된다.

```markdown
## 작업 순서
1. 읽기   — SPEC / HANDOFF / BACKLOG / git log / 참조 파일
2. 만들기 — 작업 1개만 구현
3. 확인   — 검증 명령 실행 + 합격 기준 대조
4. 커밋   — 통과 즉시
5. 기록   — HANDOFF / JOURNAL / BACKLOG 갱신 후 커밋
```

---

## 5. 커밋 순서 (Commit Timing)

**무엇**: **검사 통과 직후 즉시 커밋.** 기록·정리·다음 작업보다 먼저.

**왜**: 자율 루프는 도중에 멈춘다 — 컨텍스트 한계, 사용자 중단, 도구 실패.
통과한 상태를 커밋하지 않고 다른 일을 하다 멈추면 그 사이클의 노동이 전부 사라진다.
커밋은 "여기까지는 확실하다"는 세이브 포인트다.

```markdown
## 커밋 규칙
- 검증 통과 → **즉시** `git add -A && git commit`. 사이에 아무것도 끼우지 않는다.
- 커밋 단위 = 작업 1개. 뭉치지 않는다.
- 메시지에 검증 결과를 남긴다 (`검증: npm test 42 passed`)
- 금지: push / --force / reset --hard / 히스토리 재작성
  → **왜**: 되돌리기 어려운 조작은 사람이 깨어 있을 때만.
```

## 체크리스트

SPEC을 다 썼으면 이걸 확인하라:

- [ ] 합격 기준에 **실행 가능한 명령**이 하나 이상 있다
- [ ] "다른 사람이 봐도 괜찮은가" 류의 품질 관문이 있다
- [ ] 참조 파일에 **읽을 것**과 **읽지 말 것**이 둘 다 있다
- [ ] 모든 규칙에 **왜**가 붙어 있다
- [ ] 작업 순서가 읽기→만들기→확인→커밋→기록 으로 고정돼 있다
- [ ] 커밋 타이밍이 "검증 통과 즉시"로 못 박혀 있다
- [ ] 이 SPEC만 읽고 처음 보는 사람이 첫 작업을 시작할 수 있다
